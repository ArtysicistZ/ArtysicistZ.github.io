On knowing what changed in a vision pipeline

June 2026 · ~ 8 min read

In a video pipeline, most of the scene between consecutive frames does not change. The intuitive optimization is right there. Skip the unchanged parts. Recompute only what moved. Pay only for the work that matters.

The idea looks obvious until implementation begins. Then a quiet circularity emerges, the kind that takes a while to articulate and longer to accept. Skipping the unchanged tokens requires a way to identify them. Every way of identifying them is either too coarse to be safe or too expensive to be worth it.

The natural first approach is pixel-level change detection. The second is feature-level change detection. The third is a learned change predictor. Each fails for a different reason, and the failures rhyme.

Pixels are noisier than expected

It would be convenient if “the scene has not changed” were a property of the pixels. If the L2 distance between corresponding patches in consecutive frames is small, the patch is unchanged. A few minutes spent on real footage reveals what every video codec engineer already knows. Nothing in a video is truly static.

Camera sensors have shot noise. Auto-exposure and auto-white-balance shift global statistics frame to frame. A handheld camera jitters at the sub-pixel level. Outdoor lighting changes continuously. Even with a tripod, an indoor scene under fluorescents flickers at frequencies the sensor partially aliases. The L2-distance histogram for two consecutive frames of a static scene is not concentrated at zero. It spreads across a wide band. Any threshold either accepts too many false positives (treating moving regions as static, contaminating downstream features) or rejects too many true negatives (recomputing nearly everything, defeating the optimization).

Codec engineers solved a version of this problem decades ago with motion estimation, sub-pixel alignment, and rate-distortion optimization. H.264 and H.265 are industrial-grade change-detection systems. The cost is high. A modern video encoder is not free. Even with hardware acceleration it has nontrivial latency. Spending that much compute to identify which patches changed already represents a sizable fraction of the work the optimization was trying to avoid.

Features change in ways pixels do not

The natural fallback is to compare at the feature level. Maybe the pixels of a moving shadow change, but the high-level features stay roughly stable. What matters for downstream tasks is the feature representation. So compare layer outputs frame to frame, gate on feature similarity, recompute when features have drifted.

The logic is sound. The implementation reveals the trap. To know whether the features changed, the features have to be computed. The whole point was not to compute the features. One full encoder pass has been replaced with one full encoder pass plus a comparison step, which is strictly worse.

Real systems escape this by comparing features at an earlier layer (cheaper) and gating later-layer recomputation (the expensive part). Eventful Transformers (Dutson et al., ICCV 2023) does exactly this. The initial patch embeddings always get computed. Thresholded gating decides which tokens get their self-attention layers recomputed. The savings are real, 2 to 4× on detection and action recognition benchmarks. They come from skipping the expensive attention layers for static tokens, not from skipping the encoder entirely. The patch projection still runs. The gate evaluation still runs.

And the gate has its own failure mode. The decision rule is local: is this token's input similar to its previous input? The consequence is global. Skipping a token's recomputation means the cached K and V for that token become approximations whose error propagates into every other token's attention output. Local gating, global error. The accuracy degrades under high motion, in a way that is hard to bound a priori.

The learned-predictor approach

A separate lightweight network can be trained to predict which tokens will change. Now the system no longer depends on pixel statistics or on running the encoder partially. A dedicated model takes the previous frame's features and the current frame's pixels and outputs a change mask.

This works in principle. In practice, the predictor has to be accurate enough that its mistakes do not degrade downstream accuracy. That accuracy bar implies nontrivial capacity. Once that capacity is spent, the predictor's cost competes with the encoder cost it was supposed to save. Good predictors are not cheap. Cheap predictors are not good. Useful work gets done to decide which work to skip, and the savings collapse.

The pragmatic version uses scene priors instead of learned predictors. MaskVD (2024) combines static masks (regions usually background in driving scenes) with dynamic masks (previous-frame detections plus a small motion buffer) to mask out 80 percent of input patches while maintaining detection performance. It works because the prior is genuinely task-specific. In driving, the relevant content is mostly on the road, and the road behaves a particular way. The technique does not generalize to depth estimation, to indoor agents, or to any domain where the relevant content can appear anywhere in the frame. Accuracy gets paid for with assumptions about the data distribution, and the bill comes due when the data shifts.

The shape of the problem

This circularity, where skipping work requires information that requires work to produce, is not unique to vision. It is a recurring pattern wherever someone tries to make a computation incremental.

LLM speculative decoding. A small draft model predicts the next few tokens; the big model verifies. The cheap predictor is acceptable because verification is cheap, one forward pass over a few tokens. The math works because verification is parallelizable. Without that, the scheme collapses.

Build systems. Incremental builds work only when dependency graphs are honestly declared. An undeclared dependency (an environment variable, a clock-dependent test, an implicit include) means incremental compilation either silently corrupts or falls back to a clean build. More work, not less.

Database materialized views. View maintenance is incremental only when the view's defining query supports differential evaluation. For general queries, view refresh is a recomputation.

Cache coherence. CPU caches work because the hardware tracks every write at line granularity, paying real silicon area and power for the bookkeeping. The cost is hidden from software because it was paid in the architecture.

In each case, the same trade-off appears. Avoiding redoing work requires tracking what changed. The tracking has a cost. The optimization wins only when the tracking cost is small relative to the work it lets skip. When tracking cost approaches the work itself, as it does for ViT encoder features where “what changed” is a question whose answer requires the encoder, the incremental approach loses to plain recomputation.

The cheapest way to know

The interesting thing about all of this is that the field's most successful response has been to stop asking the question. Video Depth Anything, FlashDepth, StableDPT, Online Video Depth Anything: none of them try to identify which tokens changed. The encoder is recomputed on every frame. The temporal logic lives in the decoder, where it is both cheaper to run and easier to reason about. The encoder is treated as a stateless image-feature extractor. Temporal coherence comes from a small Mamba block or a few cross-attention layers downstream. Recomputation, it turns out, is cheap enough.

This is not a defeat for the original intuition. “Do not redo work already done” remains a good intuition. The correction is about where the cost lives. The encoder is expensive but stateless, so recomputation has bounded cost and bounded latency. The temporal logic is cheap but stateful, so caching there is both safe (the state is small and bounded) and useful (it captures the cross-frame structure that actually matters).

When the question “what changed” is itself expensive, the cheapest move is often to stop asking, recompute the cheap-to-recompute parts, and put the caching effort where the math allows the cache to be small. Incremental is not always wrong. It has prerequisites: cheap change detection, bounded error propagation, or an architecture that respects locality. When those prerequisites are not met, holding onto the optimization because it sounds good costs both accuracy and engineering time.
